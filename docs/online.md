# 联机对战

正式站点：https://dragon-ball-budokai.pages.dev/ 。首页进入「联机对战」，选择三个房间之一创建或加入；每房最多两名选手。房间内复用本地选角、选图、图鉴和招式界面；两位玩家各自选角色，双方都能选择舞台、光照、对局规则及出界判负。更换角色或共享设置会取消双方准备，服务端校验设置版本，拒绝按旧设置准备。声音和震屏属于各玩家的本地偏好。双方准备后自动连接并开战。每回合单独结算；双方点击“与对手再战”后保留对手、规则和角色直接开下一局，可取消等待。选择“换角色 / 返回房间”可调整阵容，系列比分保留；成员离开或更换对手后重置。比分由房间服务按当前对局ID计入一次，重复结束通知不会重复加分。

两位选手实际开战后，大厅中的对应房间出现「观战」按钮，并显示观众人数。其他玩家可中途加入或随时退出，观众不占选手席位。镜头自动朝向双方中点，根据角色间距、身高、武器和屏幕比例缩放；桌面、手机都用单画面。观战时隐藏战斗控制，保留双方生命、资源、时钟和「退出观战」。对战结束或选手离开时，观众自动返回大厅。

## 房间一致性

`workers/index.js` 的一个 SQLite-backed Durable Object 协调固定的三个房间。加入、离开、准备都是无 `await` 的原子状态变化，第四个房间及第三名玩家由服务端拒绝。房主离开时，另一人接任房主并取消准备；最后一人离开时房间关闭。关闭标签页、返回首页、WebSocket 关闭均清理成员。

成员状态存于休眠 WebSocket 的 attachment，唤醒后从连接重建；不写数据库、不为房间建立定时轮询。异常断网需等服务端识别连接关闭，不能保证在设备掉线的同一瞬间清理。数据库类型用于满足免费 Durable Objects 的部署要求，当前没有 SQL 或存储读写费用来源。

## 请求与同步

- 进入大厅才建立一条 WebSocket。房间状态变化后服务端推送；等待期间无 HTTP 轮询。
- 每 45 秒一个 ping，由 WebSocket auto-response 回复，不唤醒对象。
- 两人加入后协商 WebRTC DataChannel。SDP 和 ICE 候选只在建立连接时交换，STUN 使用 Cloudflare 免费端点；未配置收费 TURN。
- 直连成功后战斗包由浏览器互传，不经过 Worker。输入采样与呈现每帧执行一次，房主在本帧模拟完成后、渲染前发送模拟记录，避免把新数据留到下一帧。另一位玩家在按住状态改变或产生动作的采样帧立即发送输入。直连包不占服务器战斗请求。
- 五秒未建立直连时，沿用已有 WebSocket 中继；权威模拟记录按约30Hz、33.3毫秒周期发送，保留周期相位，避免60Hz渲染下长期降为50毫秒一批。低帧率设备仍受实际模拟频率限制。
- 客机按键不等待房主的中继批次。视角方向变化在中继时最多每50毫秒发送一次；无输入变化不发送新输入，但有待确认数据时仍可能发传输回执或重发。
- 客机仅对显示位置、步行动作和普攻前摇做本地预测，相机跟随预测位置；收到房主数据后平滑校正。预测最长 250 毫秒，尊重行动限制和地图边界，不修改真实坐标、伤害、碰撞或资源。延迟估计复用现有输入和帧包的回执，不增加探测请求。普通攻击的预显示在回执后停止。
- 对局由房主推进原有120Hz战斗引擎，客机按相同种子、帧时间和紧凑输入重放；每批检查生命、气、坐标、状态时间及随机种子。传输缺口先补齐再交给模拟，不跳过帧；真正的模拟状态偏差交由会话层校验和处理。
- 观众通过已有大厅 WebSocket 订阅当前房间。房主仅在存在观众时，每 100 毫秒发送一次画面快照，服务端只转发给该房间观众；没有观众时不发送观战帧。快照包含双方姿势、形态、生命和资源、投射物、临时技能对象及地图道具状态；中途加入从当前画面开始，客户端平滑插值。观众不运行战斗模拟、不发送战斗输入、不建立选手之间的 DataChannel，服务端拒绝观众修改对局和非房主发送观战帧。消息有大小、模型复杂度和字段校验，断线超过 15 秒返回大厅。
- 观战快照在本帧战斗记录发送之后采集；大厅WebSocket积压达到8KiB时跳过这一张观战画面。房主快照控制在24000字符以内，优先传双方状态，地图破坏状态轮转分批发送；不合规格的装饰对象单独跳过，不能阻断整张画面。
- 新观众通过`watch.flow`启用确认流控：服务端对每位观众至多保留一张已发送、待应用确认的画面。等待时丢弃旧姿势与旧特效，按地图对象索引合并尚未送出的变化；确认后在下一次发布时发送最新姿势，合并后的快照最多32000字符。观众按渲染帧合并处理收包，应用完成才发`spectator-ack`；发送暂时失败时保留确认重试。地图未变化时不重复更新破坏批次，观战不重建仅战斗碰撞需要的空间索引。新客户端连接旧服务仍可观战，旧观众沿用原有推送路径；完整收益需要双方刷新且Worker同时更新。
- 观战首帧未到与画面超过1.5秒未更新时，在场景顶部显示等待提示。流控限制的是排队长度，高往返延迟下观战更新频率会降低；它不会消除物理网络延迟。大面积破坏会逐页补齐，人物画面优先显示。
- 观战帧会经过 Worker，直连对战有观众时同样产生服务端消息消耗；沿用大厅总连接数上限 64。观战不是无限免费服务。

这是朋友间的房主权威对战，房主浏览器负责模拟，没有服务器防作弊裁判。公网延迟影响输入响应，代理、严格 NAT 或不支持 WebRTC 的浏览器会使用中继。没有创建账号或排行榜。

## 传输恢复与消息预算

协议3在每个对局ID内为开始、输入、战斗记录和退出统一编号。接收方按序交付、累计确认，迟到或重复包不会再次执行动作，也不会把已松开的按键恢复为按住。确认可以附在正常包中；没有正常上行时，待确认数据最多约每50毫秒发一次独立回执。传输回执只表示已交给会话层，和帧包内“房主已消费输入”的回执含义不同。

直连积压到64KiB、发送失败、通道关闭，或最老未确认包超过自适应确认期限时，双方通过路径epoch切到中继。确认期限至少1500毫秒，有有效往返样本后取1500毫秒与两倍RTO的较大值，避免慢但正常的直连被固定750毫秒阈值误判。序号跨路径连续，旧路径未确认数据从中继补发；旧直连包晚到仍可补缺口，但重复包被丢弃。恢复服务每25毫秒检查队列，首次RTO为750毫秒，之后按确认往返时间及波动调整到250–3000毫秒；重传记录不用于往返采样，重复超时做有界退避。缺口请求最多列出16条实际缺失记录，一次补齐短突发丢包；旧客户端仍可仅请求首个缺口，切路补发所有未确认记录；没有新流量时仍会重复请求尚未补齐的缺口。每次恢复包最多16条记录，正常批量目标约14Ki字符，不将大型历史无界堆进WebSocket。

每方向最多保留256条待确认/待排序记录，各自有512KiB字符串数据预算；最老待确认包超过10秒或恢复窗口溢出时明确结束，不能无限增长或静默丢帧。该预算是序列化数据的保守计量，不是浏览器进程内存上限。对局结束、离房和重赛更换对局ID时清理历史与恢复定时器。房主待发模拟记录只有被传输队列接管后才移除，底层send失败不会直接遗失记录。

Worker采用每连接token bucket：战斗90条/s、恢复与回执72条/s、观战帧及观众确认12条/s、信令20条/s、其他控制8条/s；同时限制总量180条/s及UTF-8流量768KiB/s，并允许有界短突发。观战与战斗分别计量，30Hz战斗加10Hz观战不会触发原先40条固定窗口的误断线。单消息仍限制49,152字符；恢复包内逐条验证选手权限，客机不能通过恢复包注入房主帧，观众不能发送选手数据。无效JSON也计入预算。

`online.exportDiagnostics()` 包含切路原因、epoch、待确认/待排序数量、重发与去重计数、自适应确认往返估计与RTO、WebSocket积压字节，以及观战接收/应用/合并数量和应用耗时。异常事件保留WebSocket关闭代码、原因及关闭前的传输统计。应用层确认往返包含浏览器调度，不等于纯网络RTT。恢复包、回执和提高后的中继频率会增加服务器消息消耗；本地检查通过不等于公网零丢包、零延迟或无限免费。

## 战斗版本与异常记录

战斗包带协议版本和规则指纹。规则指纹包含十四人普通攻击配置、角色配置、防御规则及手动维护的模拟修订号；修改模拟行为时须更新修订号。开战、确认、输入和模拟帧接收均校验，旧页面与新页面不能混用；不一致时停止开战/对战并提示双方刷新。返回房间控制包仍可处理，避免旧版本无法退出。

每页保留最近120条网络诊断事件，记录房主/客机、直连/中继、接收时间、模拟时间、帧批序号、输入时间戳和输入片段，以及版本冲突或重放异常。结算的“导出对局记录”同时导出这些事件。另保留最近10份异常发生时的事件片段，避免恢复后的正常流量覆盖失同步前的输入。导出包含对局ID、角色、规则、地图、时钟来源及最近200份客机输入确认样本。区分版本不一致、传输中断、模拟分歧和状态恢复失败；这些记录不是整场输入录像。

设备动作时间戳只用于诊断，不进入战斗输入或状态哈希。记录房主本地设备到权威接受的时间、客机输入序号与同一客机时钟测得的确认往返时间、房主接受到接触的模拟时间。接触事件关联启动该攻击的输入序号，包括收招期间缓存后执行的攻击；不能把动画出现时间当作判定响应。双方设备时钟未经同步，不能用跨设备时间戳相减声称单程延迟。75ms注入验收验证记录链路，尚不能认定公网完美格挡公平。

## 完整战斗状态恢复

`battle-state.js` 与 `state-codec.js` 保存进行中的逻辑状态及必要实体模型。包括双方攻击及队列、控制/投技引用、技能冷却、形态、资源、防御、输入边沿、未结算命中、投射物/召唤物/掩体、地图道具/破坏状态、随机状态、模拟时钟与累计器。对象图保持循环与身份引用；未知函数/类和危险字段明确拒绝。外观动画、音频句柄和本地显示预测不作为权威状态。地形装饰裂痕等随机视觉不进入战斗哈希；破坏后的逻辑与可见性必须恢复。观战快照仍为独立画面协议。

客机检查点偏差后暂停重放并请求房主完整状态。双方暂停模拟和输入，按12000字符片段、至少20ms间隔发送，最多200万字符；待确认片段达到128条或约384KiB时，保留当前片段等待确认释放空间，不把短时拥堵当作恢复窗口溢出；客机验证完整逻辑摘要、重建并再次校验，双方确认后从保存的模拟序号继续。超过12秒、数据无效或同一局恢复超过两次，明确返回房间并留下异常记录。传输补发与完整状态恢复分别处理消息缺口和模拟偏差。

JSON保存/载入和固定输入未来重放覆盖十四人攻击、技能、必杀、特殊形态，以及投技、控制、掩体、地图破坏和仙豆时钟。实测重建耗时为百毫秒量级，目前适合暂停后恢复。真实预测/回滚仍未实现；要支持120Hz回滚须避免重建场景/模型，设计常驻逻辑状态的快速复制、逐帧输入日志和重算预算，再做公网公平性评估。

## 本地开发和测试

```sh
npm run dev:online   # 联机服务，127.0.0.1:8787
npm run dev          # 网站，127.0.0.1:5173
npm run build
npm run test:online  # 真实 workerd + 直连/中继/容量/手机/四浏览器观战
```

GitHub Actions使用SwiftShader软件渲染。联机功能测试等待角色实际移动到位后出拳，冷启动加载允许30秒完成，房间布局检查等待界面可见，避免把固定墙钟等待误当作已执行的战斗帧。150毫秒延迟测试在短测量窗口内使用Playwright浏览器时钟推进真实的游戏回调：50毫秒内检查显示位移，40毫秒内检查普攻预显示及权威攻击状态；窗口外恢复正常时钟。WebSocket、WebRTC、Worker与房主权威模拟仍使用实际实现。

macOS可用`DB_SOFTWARE_GPU=1 PLAYWRIGHT_CHANNEL=chrome npm run test:online`复现软件渲染环境。联机配置继承基础浏览器配置，保留该环境变量的选择。

软件GPU下，联机功能测试在首帧前降低绘制分辨率、关闭阴影，并限制WebGL重复绘制为每秒一次；模拟、输入、网络回调和角色姿势继续正常推进。画面检查由独立的浏览器回归覆盖。四浏览器观战测试先加载全部页面再发动限时四臂形态；快照检查期间短暂暂停房主战斗模拟，双方浏览器时钟、网络确认与快照发送继续运行，检查完形态后恢复对战验证移动与输入隔离。蓄气等待按实际资源值验收。

CI先运行静态检查与单元测试，再分别运行完整浏览器、离线导出和联机检查；三个浏览器任务并行执行，独立记录失败产物，不共用一个20分钟任务预算。完整回归实测任务约19分钟，预算为30分钟；联机与离线各为20分钟。

离线单文件保留本地玩法，联机需打开网页版。生产网页默认连接同域名 `wss://dragon-ball-budokai.pages.dev/api/online`，由 Pages Function 通过 Durable Object binding 直接连接现有三个房间的协调对象，浏览器不再访问 `workers.dev`。`public/_routes.json` 只将这一个路径交给 Function，其余网页资源仍走静态服务。每次进入大厅仍只建立一条 WebSocket；连接 10 秒未收到房间状态会停止等待，提供手动重试，不增加自动轮询。`VITE_ONLINE_URL` 可覆盖地址；本地由 Vite 将同域入口转发到 8787。

## 部署

前端继续由 GitHub `main` 推送触发 Pages 构建。联机 Worker 独立配置在 `workers/wrangler.jsonc`；修改后端后先执行测试，再发布：

```sh
npm run deploy:online
```

使用有 Workers Scripts 写权限的现有 Cloudflare 登录；只用于 Pages 的凭据权限不足。`cf` 用于资源与 Pages 设置，Wrangler 用于这个已配置的独立 Worker，不在未迁移的根目录调用 `cf build/deploy`。

如果双方已经进入战斗，大厅仍显示“正在连接”且没有观战按钮，先检查联机 Worker 是否与前端同步发布。旧 Worker 会对 `playing` 指令返回“不支持的操作”，房间状态也不包含 `match.playing` 和 `spectators`；只发布 Pages 或推送前端不会更新这个独立后端。2026-10-10 已在正式入口复现此问题。后端发布后应实际确认开战状态、观战订阅和画面转发，而不只检查网页构建成功。观战快照同时需要将仙豆生成结束后的 `Infinity` 调度值转换成有限值，避免整帧被校验拒绝。

本次更新已发布前端 `3d692bf7` 和联机 Worker `7dd3a700-4673-46b6-9a29-e97593440d6a`。74 项单元测试、仙豆耗尽及十四角色观战快照回归通过；正式站点两位选手、桌面和手机观众的中途加入、退出、重入与对局结束清理测试通过。前端发布包以当时正式源码 `47c9cb4` 加本次按钮与快照改动构建，未包含其他尚未提交的战斗和 HUD 修改。

后端只接受正式 Pages 和本项目分支预览页面的 Origin，限制消息大小与每连接发送频率。测试容量压力仅针对隔离的本地服务；设置 `ONLINE_BASE_URL` 可验证线上两人对战、观战及手机入口。观战涉及前端和 Worker 协议变更，发布时需要同时更新两者；本地验收不表示线上已发布。
