# 观战与弱网修复验收

日期：2026-10-10。起点：`5820087`。反馈来自混合设备，尚无地区、浏览器和故障记录。以下结论来自可重复的本地测试，不表示已还原每位用户的现场，也不表示已部署。

## 已复现的缺陷

首次运行 `node --test tests/unit/online-resilience.test.js`，四项均失败：

1. 900 个受损场景物件使观战消息超过 Worker 的49152字符上限。旧代码只删除特效，不限制地图数据；观战与战斗共用连接，因此可触发房主连接关闭。
2. 一个球体装饰的分段数为96，超出观战协议复杂度限制；旧代码因此拒绝整张快照，人物画面也不再发送。
3. WebSocket 已积压64000字节时仍发送观战帧，继续延后同通道的战斗消息。
4. 无丢包、600毫秒往返延迟下发送120条战斗记录，固定250毫秒的重试又发送了240条重复记录。

实际浏览器弱网验收进一步发现：连接从低延迟突然上升到约600毫秒时，提前重发会使新RTT样本一直被排除；连续缺帧如果只请求一条，也会叠加多个往返。已补充延迟突变单元测试，并改为超时退避及有界批量缺口请求。

另外复现了高延迟下完整状态恢复的队列溢出：1.2 MB逻辑状态、600 ms往返，原先按20毫秒继续发分片，会在确认返回前撑满512KiB待确认预算并中断对局。分片发送现按队列容量等待；不降低完整性检查，也不提高内存上限。

## 修复与取舍

- 房主观战快照最多24000字符；破坏状态轮转分批补齐，人物与即时姿势优先。无效装饰单独过滤。观战捕获移到权威战斗记录发送之后，WebSocket积压达到8KiB时跳过当次捕获。
- 新观众每应用一帧返回确认，服务端每人最多一帧在途，确认后的下一次发布使用最新姿势。未送出的地图变化按对象合并，并在32000字符以内逐批排出；旧动作和特效不排队。高延迟观众会降低刷新率，这是限制积压的明确代价。
- 观众把同一展示帧前收到的快照合并后应用一次；不丢地图变化、不重复构建无变化的破坏批次、不再重建观战不使用的碰撞空间。添加首帧等待和画面停更提示。
- 重传根据应用确认往返时间和波动调节，排除重传样本，并做有界退避。请求缺口时一次列出最多16条实际缺失记录，避免逐条补包叠加多轮往返；含重传的累计确认不作为RTT样本，避免把等待缺口的时间混入估计。仍保留按序执行、去重、队列大小及超时限制。慢但健康的直连不再因固定750毫秒期限切路。
- 导出记录增加确认往返估计、RTO、发送积压、观战应用耗时，以及关闭代码和关闭前的统计。

RTO的平滑和重传样本排除借鉴[RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html)；本实现是WebRTC/WebSocket之上的应用恢复层，初始值、上下限及恢复窗口针对游戏设定，不声称实现TCP规范。浏览器发送积压依据[WebSocket bufferedAmount](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/bufferedAmount)，它表示尚未发出的字节，不表示对端已应用。

## 同条件前后对照

`performance/online-resilience-benchmark.mjs` 使用当前 `OrderedDelivery` 和从起点Git版本提取的实现，各发送120条记录、20Hz，FIFO队列注入双向对称时延，无丢包，最终全部按序交付。结果保留在忽略目录，不进入发布包。

| 注入往返延迟 | 原实现重复记录 | 修复后重复记录 | 交付记录（前/后） |
| ------------ | -------------: | -------------: | ----------------- |
| 600 ms       |            240 |              0 | 120/120           |
| 1200 ms      |            480 |              1 | 120/120           |

数字是重传的应用记录数，恢复包可以包含多条记录，不能据此直接推算网络包数或字节下降比例。模拟时延未改变，收益是消除不必要的重传和积压，并非把600毫秒网络变成低延迟网络。

## 验证记录

- `npm run test:unit`：最终101项单元测试通过，包含原始四项复现、1800个地图物件逐页覆盖、慢观众合并、确认重试、1200 ms健康直连、延迟突升、突发缺帧与1.2 MB状态恢复。
- `npm run lint`、`npm run format:check`、`npm run architecture:check`及Vite生产构建通过。构建仍有原有的大分包提示。
- 隔离的真实本地Worker和Chrome完成一轮12项核心联机回归：容量与清理、直连/中继实战、150 ms客机显示预测、桌面/手机尺寸观战、同帧发送、切路去重、30Hz中继消息预算、两条路径的完整状态恢复、慢观众追帧及弱网恢复。这一轮关闭WebGL重复绘制，仅用于网络与功能验收。
- 之后保留真实WebGL绘制，重新通过四浏览器观战，以及双向250–350 ms延迟、一次900 ms断流、补包后输入、再注入状态分歧并完整恢复的验收。最终弱网样本中房主确认往返估计约644 ms，双方待排序数量为0，对局继续且新按键生效。原有测试会降低绘制像素比，未修改产品画质参数。
- 慢观众阻止应用确认1.8秒期间只收到一帧；释放后跳到新序号，并补齐实际地图的328个受损物件。900/1800物件是单元压力夹具，不冒充当前这张地图的物件数量。
- 实际绘制截图已检查，保留在忽略目录：`performance/online-resilience-desktop.png`、`performance/online-resilience-mobile.png`。没有实体手机、Safari、移动运营商或跨地区公网验收。

本地端口5199/8799和构建目录独立于日常开发；最终验收期间不修改被测Worker或前端。中途发现的测试环境问题（默认Playwright浏览器缺失、地图数量假设、等待恢复消息的时序）均已定位并修正，最终使用已安装Chrome。改动未提交、未推送、未发布。

## 后续优先级

1. 上线时同步更新Pages与独立Worker，并让选手及观众刷新；在同地区不同运营商、跨地区和手机热点记录输入到权威确认的分位数、切路原因、关闭代码及设备帧时间。先用现场记录区分网络路径、设备暂停和模拟异常。
2. 真正断线续战需要短期房间保留、不可猜测的恢复身份、旧连接失效处理、双方状态恢复确认，以及超时释放席位。当前关闭WebSocket仍结束对局；这次验证的900毫秒断流属于连接未关闭时的补包。
3. 依据路径实测评估TURN与中继区域。当前STUN与单一大厅中继架构未变，没有开通新服务或新增费用配置。
4. 再推进逻辑状态快速复制与逐帧回滚。当前完整状态恢复会重建模型，不能直接用于每帧回滚；本轮保留房主权威判定，没有用显示预测修改伤害或碰撞。
