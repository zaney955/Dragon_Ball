# 联机前三项优化验收

日期：2026-10-10。范围对应 `online-latency-plan.md` 的前三项：同帧发包、30 Hz 中继、跨传输路径可靠交付。未发布线上。

## 已实现

1. `online.frame()` 继续负责输入采样与显示预测；新增 `online.flush()` 在本帧战斗模拟之后、渲染之前发送。模拟记录只有被有界传输队列接管后才移除。
2. 中继由约100毫秒一批调整到1000/30毫秒，按周期余数保留相位。Worker由原有每秒40条固定限制改为战斗、观战、信令、控制、恢复分类的token bucket，同时保留连接总量、字节量和单包上限。
3. 每个对局拥有跨DataChannel和WebSocket连续的传输序号、累计确认、重发队列和接收排序队列。拥塞、发送异常或确认超时触发单向切中继；新旧路径重复包不会重复执行动作。队列和恢复时间有上限，超限明确结束，不静默跳帧。

协议版本为3，旧页面通过战斗版本校验提示刷新。传输确认与“房主已实际消费输入”的确认分开，显示预测没有获得战斗裁决权。

## 验证方法

- 单元测试从 `OnlineTransport` 对外通道注入丢包、乱序、重复和发送异常；检查应用实际收到的顺序、次数、按键释放状态，以及队列释放和超时。
- Worker预算测试持续发送30 Hz战斗、10 Hz大观战快照和回执，同时验证洪泛限制、恢复包内的角色权限和禁止嵌套恢复。
- 双浏览器测试使用真实Chrome、WebRTC、WebSocket和本地workerd。切路测试扣留一个真实直连帧、触发拥塞切中继，随后让旧帧晚到；输入去重测试重复发送真实WebSocket输入包。
- 专项频率测试同时运行房主、客机和观众，检查实际模拟帧批发送频率和连接存活。
- 同构建调度对照只恢复旧的“下一帧发送／中继100毫秒批次”，其他传输与渲染条件一致。该对照隔离发送调度收益，不代表旧发布版本的完整对比。

## 功能验收结果

- 最后一次完整单元测试：64/64通过，其中传输、预算及连接专项16/16通过。
- 三项真实浏览器专项：3/3通过（最终独立复验约1分钟）。
- 四浏览器观战：单独复验通过（27.8秒）。
- 其他已分批通过的联机回归：真实Worker容量与断线清理、直连与中继对战、手机入口、同域连接超时重试、150毫秒延迟下的显示预测、太阳拳反向输入、雅木茶反击、双路径防御破坏与恢复、版本不一致拦截、第四地图双路径同步。
- lint、模块接口检查通过；固定构建成功，仍有既有大包体提示。

回归期间修正了三个验收问题：房间标题加入系列比分后改为检查房间身份；防御测试先检查双方破防，再等待任何一方恢复；四浏览器观战保留真实网络时钟，避免冻结确认/重发定时器。连接层也修复了普通房间推送覆盖版本冲突提示的问题。

并行浏览器任务期间曾出现秒级积压、握手超时及被中断的整批运行，未将它们计为通过。最终采用独立端口、固定构建和分项复验；没有声称一轮全量浏览器测试全部通过。其他同时进行的状态恢复与再战功能不属于本报告的完成范围。

## 同构建延迟对照

Chrome 155.0.8059.40、macOS原生Metal、本地双浏览器与workerd。每种配置按32组左右移动按下/松开操作采样；渲染帧间隔P50约16.7毫秒。四种配置均保持双方对局有效，无页面异常。

| 调度方式                 | 显式输入回执样本数 | 发送至权威回执 P50 |      P95 | 最新模拟记录发送等待 P95 |
| ------------------------ | -----------------: | -----------------: | -------: | -----------------------: |
| 直连，恢复旧的下一帧发送 |                262 |            30.0 ms |  48.2 ms |                  17.5 ms |
| 直连，本帧模拟后发送     |                258 |            13.6 ms |  23.2 ms |                   0.1 ms |
| 中继，恢复旧的100ms批次  |                 68 |            64.4 ms | 128.0 ms |                  17.5 ms |
| 中继，本帧发送+30Hz      |                102 |            19.5 ms |  33.3 ms |                   0.0 ms |

回执耗时使用客机同一个单调时钟，包含输入发送、房主等待与处理、返回传输；没有减去房主处理时间。每个返回帧仅计其明确回执的最新输入，包含方向更新；批次覆盖的其他输入未逐条统计，因此样本数不同，不应把这张表理解为所有按键的完整延迟分布。发送等待为批次中最新模拟记录的等待，不能代表批次内最老记录。每种配置仅进行一轮本机对照，后台负载与调度抖动没有完全隔离，数据不构成公网或硬件性能承诺。

原始样本：`performance/online-optimization-measurements/summary.json`及四份对应JSON。专项通过记录：`performance/online-optimization-core-results.json`、`performance/online-optimization-spectator-results.json`。

## 运行边界

测试使用独立前端5198、Worker8798、固定构建和独立结果目录，避免同一工作区其他测试共用房间、端口或覆盖构建。原始本地结果保存在已忽略的 `performance/`、`test-results/` 及 `/tmp/dragon-ball-online-optimization-e2e` 下。

本地浏览器间的测量不代表公网、跨国网络、蜂窝网络或真机触屏的延迟。传输恢复降低切路失败概率，不能消除物理传播时间。中继频率和恢复消息增加Worker流量，发布需要同时更新Worker与前端。
