# 包子山、龟仙屋重制与武道会性能验收

2026-10-10。本轮直接接入现有 `wild`、`kame`、`budokai` 地图入口，沿用战斗、越肩镜头、分屏、建筑破坏、仙豆和存档接口。图片用于场景元素和布局参考，实际交付是 Three.js 场景。

## 场景实现

包子山包含分层柱状山峰、山顶树林、近景树木与岩石、两级瀑布、溪流和水潭，以及带门廊、木栏、瓦片、窗框、台阶和烟囱的山间小屋。中央泥地战斗区保持平整，草地、石岸和远景地形在外围过渡。

龟仙屋包含粉色墙面、红瓦屋顶、墙面 KAME HOUSE 字样、百叶窗、门廊与台阶；海岛由连续网格塑形，周围布置椰树、礁石、码头、遮阳伞和长椅。海水采用单个不透明着色器，提供深浅水色、波光与岸边泡沫，没有额外反射、折射或后处理通道。

两图沿用 toon 材质和现有光照设置，支持白天、夕阳和满月。战斗边界仍为 X ±13.5、Z ±6，建筑和高树避开主要越肩镜头区域。12个可破坏小道具分布于外围。

共用的 `adventure-scenery.js` 管理建筑、植被和基础几何，`scenery-batching.js` 管理静态合批与实例化。近景树冠和远景树冠使用不同细分；色彩进入顶点色或实例颜色，静态装饰与可破坏建筑保持独立。小纹理复用现有资源生成器，岩壁贴图为256像素。

## 武道会卡顿原因与修复

原越肩镜头每帧对合并景物做两次精确射线检测。Three.js 网格的球体粗筛使用无限射线；横跨场地两侧的花园合并网格又覆盖了战斗中心，导致较短的镜头射线仍遍历大量三角面。原本机测量镜头更新中位数约61.5毫秒。

现在在地图创建后缓存障碍物世界包围盒，先按有限镜头线段排除远处景物，再执行原来的精确检测；花园按左右两侧及纵向区段分别合批。后来生成的战斗掩体仍执行正常射线检测。静态地图的包围盒不在每帧重复计算。

98块地砖使用一次实例化绘制，原地砖对象仍保存独立血量、裂纹颜色和位移；只在状态变化时更新实例缓冲。保留192名观众与建筑细节，降低远景观众、树冠和云朵的几何细分，关闭不可辨认的小观众实时阴影。旗帜顶点以30Hz更新，云朵只改变整体变换。

测量环境：本机 Apple M4，Chrome/ANGLE Metal，1440×900，桌面像素比1。对照构建使用同一份战斗代码，只将地图相关模块恢复为重制前版本；两边均为生产构建。原始结果和实际游戏截图保存在忽略提交的 `performance/maps/`。

武道会镜头更新的72组位置/方向采样中位数从48.5降至4.6毫秒，P95从56.2降至5.0毫秒。包子山与龟仙屋的新镜头采样低于浏览器计时分辨率，不能解释为零成本。包子山增加了近景建筑和地形细节，三角面增加，但索引网格、几何共享与实例化使缓冲和绘制调用下降。

几何缓冲数值是去重后的几何属性与索引数组大小，不是浏览器总内存或显存。draw call 是固定实战视角下 `renderer.info` 的结果，包括可见阴影绘制；CPU提交时间不等于GPU执行时间。

另测真实AI对战：桌面1440×900与竖屏390×844、设备像素比2（渲染器上限1.65），每个场景采样180帧。旧武道会两种视口中位数均为50.0毫秒、P95均为66.7毫秒；新武道会、包子山、龟仙屋两种视口均为16.7毫秒，P95为16.7–16.8毫秒。最终构建没有页面异常或着色器错误。竖屏使用本机浏览器模拟，没有验证实体手机，也没有做长时间温度与续航测试。

## 验收结果

- ESLint、Prettier、81个模块接口检查通过，全部74项单元测试通过。
- 最终生产构建的14项地图浏览器测试通过，覆盖两张重制地图、武道会、天神殿的实战和展示视角、三种光照、越肩与分屏镜头、破坏、回血、存档恢复和资源回收。
- 两图各144组边界/方向/分屏镜头检查通过；连续三轮切换地图后几何与纹理计数没有持续增长。
- 完整独立快照回归：81项通过、26项按配置跳过、1项悟空练习失败。相同练习失败在旧地图对照构建也复现，与地图改动无关；未将这项记录为通过。

- 单文件离线版的7项验收通过，包括两图完整专项与断网打开、57项系统断言、66项少年角色断言和音频解码；没有发起网络请求。网页和单文件离线构建成功。

地图保持原有玩法接口，没有引入外部模型下载或新后处理链。性能结果只代表上述环境与采样范围；实机手机表现仍需后续设备验收。
