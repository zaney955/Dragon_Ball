# 浏览器 1v1 对战低延迟：一手资料与项目适用条件

调研日期：2026-10-10。本文记录规范、官方文档和 GGPO 源码提供的依据，以及根据当前项目代码作出的工程判断。没有部署、开通收费服务或进行公网两地实测；预期收益不是已经测得的结果。价格与平台限制以调研当天官方文档为准。

## 1. 先区分三个目标

本项目的目标应分别记录为：按键到本机第一帧响应、按键到权威结果返回、远端角色连续运动与命中一致性。网络 RTT 只是其中一项。当前房主运行权威模拟，客机接收房主逐帧输入记录并重放，显示层再预测客机移动和普攻前摇。对于必须等房主确认的结果，客机经历上传输入和接收结果两段路径；只改显示预测不会让判定更早发生。代码依据：[`session.js`](../src/online/session.js)、[`presentation.js`](../src/online/presentation.js)。

GGPO 官方将 rollback 定位为预测远端输入、先推进模拟、出错后回滚，以减少等待输入造成的手感延迟。这不等于改变物理网络传输时间。完整 rollback 与本项目当前的显示预测是不同能力。[GGPO 官方说明](https://www.ggpo.net/)

由此提出工程判断：短期先去掉额外等待、误降级与排队；长期若追求双方接近离线的完整操作手感，应研究可恢复的完整战斗模拟和 rollback。不能只凭“显示在 40 毫秒内响应”认定命中、防御、闪避已经实时。

## 2. WebRTC 通道：不能只改一个开关

### 规范事实

`ordered:false` 允许乱序交付；`maxRetransmits:0` 限制重传次数为零；`maxPacketLifeTime` 是允许传输/重传的时间窗口。后两项不能同时设置。未限制重传的通道默认可靠。`bufferedAmount` 是应用数据尚未交给网络的字节数，排除协议开销和操作系统/网络硬件缓冲；它不是端到端排队时长。低水位事件可用于恢复发送。[W3C DataChannel API](https://www.w3.org/TR/webrtc/#rtcdatachannel)

同一 SCTP association 的所有流共享拥塞窗口；各流可以独立排序，但大消息仍可能影响其他流。RFC 建议 message interleaving；不支持交错时建议消息不超过 16 KB。因此拆通道可隔离同流排序依赖，却不保证隔离拥塞或实现中的大消息阻塞。`maxRetransmits:0` 也不把浏览器变成无拥塞控制的裸 UDP。[RFC 8831 §5–6](https://datatracker.ietf.org/doc/html/rfc8831#section-5)

### 当前协议的硬约束

[`transport.js`](../src/online/transport.js) 只建一个 `battle` 通道，配置 `{ ordered: true }`。[`session.js`](../src/online/session.js) 要求 `frames.seq` 严格连续，逐个调用 `baseAdvance(frame.dt, ...)`，最后比较状态检查点；缺一批就停止对局。这些包不是可任意舍弃的绝对状态快照。

因此，直接把现有 `battle` 改成不可靠或乱序，会将弱网中的等待变成丢帧、状态不一致或退出，并不构成安全优化。客机输入也是按变化发送；按键释放包丢失会导致持续按住，一次性动作丢失会漏招，重复传输又可能重复放招。这些结论来自上述协议代码。

### 建议的分阶段协议设计

以下为工程方案，尚未实现：

| 数据                             | 第一阶段                      | 允许不可靠发送的前置条件                                |
| -------------------------------- | ----------------------------- | ------------------------------------------------------- |
| 开始、退出、版本与规则、恢复快照 | 小型可靠控制消息              | 一般保留可靠；处理重复与跨通道先后顺序                  |
| 现有房主模拟记录                 | 保持可靠有序                  | 新协议具有逐 tick 编号、缺口恢复，或完整状态恢复能力    |
| 持续按键状态                     | 可单独建低延迟输入通道        | 序号去旧、周期重发最新完整状态，确保释放能恢复          |
| 一次性攻击/变身等动作            | 可靠或应用层确认              | 动作 ID、重复去重、确认与有限重发，不能只附在一次包中   |
| 完整可替换显示快照               | 可考虑 unordered + 有限可靠性 | 明确 tick/epoch，只用最新完整快照，保留独立可靠恢复路径 |

在不可靠输入上附带最近若干 tick 的冗余输入，可用后续包弥补短暂丢失，但必须明确确认边界、内存上限及窗口耗尽策略。重传旧模拟记录与发送最新可覆盖状态的语义不同，不要用一个“丢弃过期包”规则处理所有消息。

大规模状态恢复和资源传输应与实时输入错峰，并限制消息大小及总吞吐。单独通道不能代替背压。二进制编码只应在序列化耗时和包量证据明确时引入，不会自动解决一个 RTT 的判定等待。

## 3. 连接选择与降级需要独立状态机

当前 `packet()` 在通道尚未打开或 `bufferedAmount >= 65536` 时设置 `forceRelay = true`，之后该局持续中继；源码注释是为了保持顺序。它没有对“还在协商”“暂时背压”“确实不可达”分别建模。因此值得实验验证：短暂异常是否会把本可直连的整局锁在中继模式。依据：[`transport.js`](../src/online/transport.js)。

建议先记录降级原因、发生时间、通道/ICE 状态、缓冲量与持续时长，再改变阈值。可靠重放模式发生切路时应设 epoch 与确认屏障：确认哪一 tick 已到达，再继续/补发，拒绝旧路径迟到包。不能简单删除 `forceRelay` 后在 WebSocket 和 DataChannel 间逐包跳转，否则跨路径到达顺序没有保证。

背压应同时观察字节数和最老待发送消息年龄；只用 64 KB 不能表达“这批消息已经落后多少毫秒”。能合并的是完整最新状态；必须连续执行的模拟记录只能可靠补齐或从完整快照恢复。以上为基于现有重放约束的设计建议。

## 4. TURN 与 Durable Object：连得上和延迟低是两件事

Cloudflare TURN 支持 UDP、TCP、TLS。UDP 主端口 3478、备选 443；TCP 主端口 3478、备选 80；TLS 主端口 5349、备选 443。官方表示 Anycast 将客户端接入邻近网络位置，但这不保证两位玩家之间最低 RTT。当前文档给出的每个 allocation 限制包括约 5–10 kpps、50–100 Mbps，超限会丢包；这些是平台容量边界，不是建议本游戏达到的发送频率。[TURN 服务文档](https://developers.cloudflare.com/realtime/turn/)

截至调研日期，SFU 与 TURN 共用每月 1,000 GB 免费出站额度，超出为 $0.05/GB；其他 Workers/DO 费用另计。TURN 的计费流向有自己的定义，不能只拿应用层 JSON 大小当账单；以官方计量为准。[Realtime 定价](https://developers.cloudflare.com/realtime/sfu/platform/pricing/)、[TURN 计费 FAQ](https://developers.cloudflare.com/realtime/turn/faq/)

Cloudflare 中国网络不承载该 TURN 流量，中国大陆用户连接境外节点。因此面对大陆玩家应实际比较运营商和跨境路径，不能把“Cloudflare 全球网络”当成大陆本地中继的保证。[TURN 区域 FAQ](https://developers.cloudflare.com/realtime/turn/faq/)

TURN key 应只放服务端，由服务端为客户端生成有限有效期的 ICE 凭据；不能把长期密钥写进前端静态资源。[生成 TURN 凭据](https://developers.cloudflare.com/realtime/turn/generate-credentials/)

本项目可比较 WebRTC 直连、TURN/UDP、TURN/TCP/TLS 和现有 WebSocket 中继。TURN/UDP 是在直连失败时维持 DataChannel 传输语义的候选方案，是否更快需测。TCP/TLS 解决可达性时也可能引入底层重传等待；将 DataChannel 改为不可靠不能消除其底层 TCP 等待。

### DO 放置的项目影响

DO 请求需要转发到对象所在位置。官方当前说明对象创建后不会动态迁移，首次 `get()` 的位置或首次指定的 `locationHint` 影响放置；hint 是尽力而为，不保证目标区域。[DO 数据位置](https://developers.cloudflare.com/durable-objects/reference/data-location/)

本项目 [`workers/index.js`](../workers/index.js) 和 [`functions/api/online.js`](../functions/api/online.js) 都使用 `getByName('three-room-lobby-v1')`，三个房间共享同一对象。代码没有证明线上对象实际位于哪里，也不能假定它随每个玩家就近运行。

工程判断：若中继占比较高，按对局或区域建新对象、在双方合理位置放置，再测双方 RTT，可能比继续让所有对局共用一个固定对象更有效。但给既有名字追加 hint 不等于搬迁，且玩家各自距节点最近不等于双方总路径最短。直连战斗不经过 DO，调整 DO 位置主要影响大厅和中继，不会缩短已建立 P2P 的 RTT。

### 当前可核实的 DO 成本与容量

免费计划为 100,000 requests/day、13,000 GB-s/day；付费计划包括每月 100 万 requests 和 400,000 GB-s，超额分别 $0.15/百万 requests、$12.50/百万 GB-s。入站 WebSocket 消息仅计费时按 20:1 折算，出站消息不收这项消息费用；指标和实际处理负载不按 20:1 缩小。休眠能减少空闲持续时间费用，不能把活跃战斗视为免费。[DO 定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)

单个对象的官方请求吞吐软上限为 1,000/s，实际取决于处理工作量。这不是整个账号总量，也不是浏览器消息率推荐值。[DO 限制](https://developers.cloudflare.com/durable-objects/platform/limits/)

因此降低中继批间隔时必须同时记录每局入站包率、观战额外包率、CPU 和额度增长，而非只提高发送频率。

## 5. 测量：不能把 ICE ping 当操作延迟

从 `transport.selectedCandidatePairId` 找当前候选对，再关联 local/remote candidate，记录 candidate type、protocol、relayProtocol。`currentRoundTripTime` 是 STUN 检查/consent 的最新往返秒数；`RTCDataChannelStats` 提供消息和字节计数，没有一个通用的 DataChannel 应用层丢包率字段。`availableOutgoingBitrate` 依赖 RTP 的带宽估计机制，纯 DataChannel 场景可能缺失，不应当作 SCTP 可用带宽保证。[W3C WebRTC Stats](https://www.w3.org/TR/webrtc-stats/)

建议为本项目新增/完善以下测量，属于设计建议：

| 指标           | 采集方式                                                                   | 能说明什么                                                 |
| -------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 本机输入到显示 | 同一客户端记录输入事件、模拟首次消费、首次画面提交；关键场景用高速录像复核 | 显示响应；rAF 回调不等于屏幕已经发光                       |
| 输入到权威确认 | 输入 ID/序号被房主实际消费后，随返回帧确认；客机用自己的时间戳相减         | 包括上传、模拟调度、批等待、返回与处理的实际体验           |
| 网络往返       | ICE RTT 与小型应用 ping/ack 分开记录                                       | 区分路径 RTT 与应用排队；不能直接把一半 RTT 当准确单向时延 |
| 发送/接收停顿  | bufferedAmount、待发队列最老年龄、帧到达间隔、序号缺口/恢复时间            | 看抖动、背压、HOL，而非只看平均 ping                       |
| 预测修正       | 修正次数、位移分布、动作撤销、确认 tick 落后量                             | 看“即时显示”是否以频繁拉回和错误动作为代价                 |
| 设备帧时间     | 模拟、序列化、收包重放、绘制分别记录 p50/p95/p99                           | 查网络已经快但主线程/GPU 卡顿的情况                        |

两个客户端的 `performance.now()` 原点不同；未经同步不能直接相减得单向延迟。现有回执复用客机时间戳并减去房主处理耗时，适合近似网络往返估计，但还应保留“未扣处理时间”的完整确认延迟，避免把本可优化的等待从指标里减掉。依据：[`presentation.js`](../src/online/presentation.js) 的 `snapshot()` 与 [`session.js`](../src/online/session.js) 的 `ack.processing`。

验收建议：同局域网、同地区不同运营商、跨地区、移动热点；直连和中继分别跑；人工注入延迟、抖动、丢包与短突发停顿；Chrome/Firefox/Safari 及低性能手机分别记录。公布注入位置和方向：在 JS 回调里延迟收包无法证明真实网络丢包下 SCTP 重传、拥塞和 HOL 的表现。测试工具时钟下的显示测试也不能替代真实刷新率和公网测试。

## 6. 真正 rollback 需要哪些工程基础

GGPO 要求完全确定性的引擎。其接口要求保存整个游戏状态、恢复旧状态，以及在回滚时逐帧推进；核心实现在发现最早错误预测后加载旧帧，再重算到当前帧。这些能力不会由一个 WebRTC 参数提供。[GGPO 概念](https://www.ggpo.net/)、[GGPO 回调接口](https://github.com/pond3r/ggpo/blob/master/src/include/ggponet.h)、[GGPO 同步核心](https://github.com/pond3r/ggpo/blob/master/src/lib/ggpo/sync.cpp)

本项目已有固定子步进、输入编码、随机种子与重放检查，是有用的起点。但当前客机按房主发来的浏览器帧 `dt` 和输入序列重放；这不能证明两端脱离房主逐帧记录后仍能独立预测并得到同样结果。现有检查点只覆盖部分状态，也不等于完整可加载存档。

建议的改造顺序如下，均为工程建议：

1. **确定模拟边界。** 固定 tick 编号和固定 dt，输入归属 tick；网络计时、渲染插值、摄像机不参与决定伤害。不要因不同屏幕刷新率改变同 tick 的输入消费次数。
2. **完整保存恢复。** 覆盖角色状态机、技能计时、资源、连招、抓取关系、投射物/召唤物、地图物件、随机数状态、输入边沿、事件 ID 与终局条件；保存数据与 Three.js/DOM/音频对象分开。
3. **先验证重放确定性。** 同一初始状态与输入脚本反复加载和重放，每 tick 比较完整逻辑状态；再跨浏览器/设备跑相同记录。GGPO 自带同步测试也是加载历史帧、重放并比较校验值，可以参考其方法。[GGPO SyncTest 源码](https://github.com/pond3r/ggpo/blob/master/src/lib/ggpo/backends/synctest.cpp)
4. **控制重算开销。** 采用有上限的状态环形缓冲；一次展示帧内可能要重算多个 tick，应避免重建渲染物件和重复内存分配。将最差回滚耗时纳入帧预算。
5. **定义预测与输入缓冲。** 预测远端持续状态时可保持上一 tick，不能无条件反复预测一次性招式。输入延迟、预测窗口和帧同步共同调节；窗口耗尽需等待或明确恢复，不是无限猜测。GGPO 本身存在 prediction threshold、frame delay 和 timesync 机制，rollback 并不意味着永远零输入缓冲。[GGPO API](https://github.com/pond3r/ggpo/blob/master/src/include/ggponet.h)
6. **分离可重放逻辑与外部副作用。** 使用 `(matchEpoch, tick, entityId, eventIndex)` 等稳定事件标识去重音效、震屏、粒子和 UI；重算期间不重复播放。错误预测的攻击音效可能需要取消/抑制，最终胜负和不可逆外部操作等确认后提交。这是从“一帧可能执行多次”的回滚机制推导的设计要求，不是 GGPO 自动替游戏解决的功能。

### 120 Hz 下怎样估算窗口

要区分**输入延迟 D**（本地输入安排到未来多少 tick 才生效）、**预测上限 W**（最多允许多少尚未确认的 tick）、**状态保留容量**（还能恢复到多早）。GGPO 的 input queue 将输入帧号增加 `_frame_delay`；同步核心则比较当前帧与最后确认帧的差，达到预测上限后拒绝继续推进。这两项不是同一个参数。[GGPO InputQueue](https://github.com/pond3r/ggpo/blob/master/src/lib/ggpo/input_queue.cpp)、[GGPO Sync](https://github.com/pond3r/ggpo/blob/master/src/lib/ggpo/sync.cpp)

在**双方 tick 相位基本一致、链路近似对称、输入采样后立即发送**的假设下，120 Hz 每 tick 为约 8.33 ms；150 ms RTT 对应约 75 ms 单程，理想输入到达落后约 **9 tick**，并非必然需要 18 tick 回滚。实际要覆盖发送节奏、接收调度、两端模拟相位差、抖动和补包时间。以下只是选型估算，不是协议保证：

```text
所需预测深度 ≈ max(0,
  ceil((单程时延高分位 + 发送/处理等待 + 正向模拟相位差) / tick时长)
  - 输入延迟tick数)
```

例如同样假设 75 ms 单程、暂无其他等待，D=2 tick 时理想缺口约为 7 tick，同时本地操作固定增加约 16.67 ms 等待。增大 W 不会自动增加每次操作的输入延迟，但会允许更长的错误预测、更大修正及更多重算；增大 D 会明确增加本地等待，却可缩小预测缺口。这是帧编号模型下的推导。

真实配置应统计“远端输入到达时，本地模拟 tick 与该输入生效 tick 的差”及最早未确认缺口，而不是直接套 RTT/2：上下行可能不对称，可靠通道丢包补齐也可能使最早缺口远旧于最新收到的 tick。状态缓冲需容纳允许回滚深度及边界状态，并依据实际重放/确认语义保留安全余量；原生 GGPO 的固定窗口数值不应原样搬到本项目 120 Hz 引擎。

本项目现有房主权威客机确认链路是客机→房主→客机；它等待结果的量级可接近完整 RTT，再加帧与批等待。不能把这条确认链路的往返等待与对称 P2P rollback 的远端输入单程迟到混为一谈。

### 架构取舍

| 路线                        | 可改善什么                           | 仍然保留的限制                                             |
| --------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| 继续房主权威 + 显示预测     | 低改动降低按键观感等待，保留现有规则 | 实际判定仍受远端输入到房主的延迟影响，复杂交互预测不完整   |
| 客机完整预测 + 房主快照校正 | 客机可以即时执行更多动作与资源变化   | 快照恢复/重放工作量大，房主裁决优势仍存在                  |
| 双方确定性 rollback         | 两端可采用一致本地响应规则，适合 1v1 | 需要完整确定性、保存恢复、预测修正；不能消除作弊或物理延迟 |
| 独立服务器权威 + 客户端预测 | 将裁判独立于玩家设备                 | 新增运维与部署区域选择，两端仍有客户端到服务器 RTT         |

本项目下一步适合先建立确认延迟和路径分布证据，并处理协议允许范围内的额外等待；同时以隔离原型验证完整状态恢复与确定性。只有原型能稳定重放全部技能，才有依据决定是否进入全面 rollback 改造。
