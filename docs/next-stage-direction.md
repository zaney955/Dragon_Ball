# 下一阶段优化与制作方向

日期：2026-10-10。目标由用户确认：**做成朋友之间能反复玩的完整小游戏。**

研究基线：当前 `main`，提交 `cc9b29b`。本轮阅读源码、现有设计和验收记录，运行单元测试与生产构建，使用本机 Chrome 实际打开生产构建，检查桌面/手机模拟画面、短时渲染和连续重开。技术方案另见 [官方资料研究](next-stage-technical-research.md)。本轮交付研究和规划，没有修改游戏功能、提交、推送或部署。

## 核心判断

下一阶段应围绕一次完整的朋友对战：**发链接 → 进同一房间 → 看懂操作 → 打完一场 → 双方愿意再来 → 换角色继续。**

目前内容数量已经够支撑这条流程：14 角色、3 舞台、差异技能、变身、破坏、训练、观战、胜利演出。主要机会是降低加入和学习成本，补齐持续对局的组织方式，并让双方在不理想网络下仍能理解游戏发生了什么。增加角色、地图和更大的特效，会同时增加平衡、碰撞、手机和联网验证成本，收益应放在这条流程完成之后评估。

“愿意反复玩”还没有真人数据证明。本文对上手和再战的判断是产品假设；对源码、构建、运行数据的描述是本轮证据。二者分别列验收门槛。

### 本机运行基线

环境：Apple M4、Chrome 155.0.8059.40、Metal、headless、1280×800、DPR 1。每个场景预热2秒、采样8秒；训练为站立陪练，CPU场景只有对方自主行动，分屏双方站立。数据包含测试入口额外模块，不能代表普通玩家完整冷启动。

绘制计数采用 `renderer.info.autoReset=false`，逐次 `renderer.render()` 取差值并按动画帧间隔汇总，计入阴影与两次分屏绘制。CPU绘制耗时是 JavaScript 调用耗时，不是 GPU 计时。各场景角色和地图不同，不能把差值全部归因于分屏。

| 场景                      | 帧间隔 P95 | 绘制次数 P50 / P95 | 三角形 P50 | CPU绘制耗时 P95 |
| ------------------------- | ---------- | ------------------ | ---------- | --------------- |
| 悟空/克林，武道会站立训练 | 16.8ms     | 578 / 578          | 614,475    | 2.2ms           |
| 悟空/比克，包子山CPU对战  | 16.7ms     | 455 / 470          | 632,105    | 2.7ms           |
| 牛魔王/皮尔夫，龟仙屋分屏 | 16.7ms     | 593 / 595          | 519,712    | 3.2ms           |

最终采样数字见本地 `performance/next-stage-audit/report.json`；该文件与截图按现有约定保持本地、不进入Git。这里的几何绘制量包含阴影重复绘制，不能当作独立模型面数。

- 三个场景的帧间隔 P95 为16.7–16.8ms，短窗基本保持60帧；这不足以推断双方持续激战或低端手机性能。
- 同一牛魔王/皮尔夫龟仙屋分屏场景连续15次重开，已上传 geometry/texture 对象数量没有持续增长。JS heap 呈周期波动，未采集强制GC后的保留堆或进程显存，不能据此宣称没有任何泄漏。
- 普通入口三个新浏览器上下文的本地可交互等待约1.06–1.27秒。这包括建模/生成缩略图，但没有真实公网限速，不能用作公网加载速度承诺。
- 手机仅模拟390×844和DPR 3，游戏实际DPR上限1.65，仍用M4渲染。Playwright官方说明模拟的是视口、触屏等浏览器参数，实体设备性能需另测：[Emulation](https://playwright.dev/docs/emulation)。

## 第一方向：完成朋友连续对局

这是本阶段最优先的功能制作。一次对局结束后还要重复准备，会让游戏在每局之间重新争取玩家注意力。建议沿用现有房间机制，加入以下流程：

1. **邀请进入指定房间。** 复制链接后对方直接看到该房间和座位状态；满员时明确提供观战或返回大厅。先保留三房间，链接只定位房间，不把它宣传为私密邀请。若以后需要专属房间，再做独立房间ID和加入凭证。
2. **联机三局两胜，可选单回合。** 区分一场比赛与一个回合，保存比分、舞台和双方角色；回合间短演出后继续，整场结束再给再战选择。观众应能跟完整场，而不是每回合被踢回大厅。
3. **双方确认再战。** 一方点击显示“等待对方”，双方同意才开始；改角色进入选角并清除准备；保留选图和偏好，避免反复配置。
4. **房间内临时比分。** 记录本次会话胜场，不做账号和长期排名；离开会话后清除，反馈保持轻量。

实现涉及 `workers/index.js`、`src/online/session.js`、`src/online/lobby-ui.js` 和 `src/match/`。服务端需要统一回合编号、比赛编号、配置版本和准备状态，不能仅修改前端按钮。重复点击、旧回合包、双方同时再战、改角、离开、观众中途加入都要有唯一结果。

**候选验收门槛：**两台设备从邀请链接到开战无需解释；同房连续完成10场比赛，不重复建连接、不混比分、不吃掉首个输入；一方退出时另一方得到明确结果；真人试玩中记录结算到下一场的时间与主动再战次数，而不是只验按钮存在。

## 第二方向：让新人很快体验到一件有意思的事

当前练习更像给已经想学某个角色的人准备的工具。第一次打开游戏的新朋友，需要先得到“我会打了”的反馈，再选择是否研究帧数据。

建议做可跳过的约90秒引导，复用真实战斗事件：靠近 → 轻击命中 → 一套简单连招 → 格挡一次 → 聚气并发动一个角色技能。每一步只提示一个操作，以实际移动/命中/格挡/技能事件推进，不通过等待时间自动完成。结束直接进入普通CPU对战或回到朋友房间。

首次推荐悟空或克林，把变身、反向操作、控制衰减等复杂条件留在已有角色玩法中。推荐选择不等于锁角色，也不让老玩家每次重做引导。

手机先做拇指区域的布局试验：移动摇杆、常用动作区、清楚的技能状态。残像、解围和拆投属于需要及时响应的能力，不能为了减少按钮数把它们藏在难打开的菜单。可比较完整布局与简化布局，让使用者选择；在测试之前不承诺“六个按钮就够”。保持输入语义与键盘一致，避免手机自动追击或自动连招形成额外优势。

**候选验收门槛：**邀请5名未参与开发的朋友，至少4名在5分钟内独立完成一次格挡、一套连招和一个技能；能说清“没能发动”是气不足、冷却还是受击。实体iPhone/Android分别测试连续移动+攻击、移动+防御、快速松键、旋转屏幕、返回前台；记录误触与手指遮挡。

## 第三方向：优化联机质量，先解决可解释性与稳定性

现在的视觉预测已经减少等待感，但尚未覆盖跳跃、闪身、特殊技能等全部动作。对这些操作，仍需要先量出显示响应和权威确认分别花多久，再决定扩大预显示还是修改同步方式。预显示不能产生提前命中、提前扣费或假的无敌。

先增加开发诊断：传输模式、输入到本地显示、输入到确认的P50/P95/P99、收包抖动、积压字节、预测校正距离、退局原因。玩家只需要理解“直连/中继、连接状态”；完整网络指标放调试页或可导出的本局记录，不占战斗HUD。

最值得优先验证的协议风险是 **DC转WS的在途消息交接**：现有通道积压后单侧永久改中继，客机又要求帧序号连续；旧DC包晚于新WS包到达时可能被判不同步。这个风险来自源码推断，本轮没有复现。下一次做网络工作时应先用隔离环境构造跨路径乱序，再决定协议修补。可靠性与顺序是独立属性，不能直接把当前需要逐帧重放的流改成“丢包也没关系”。[W3C DataChannel](https://www.w3.org/TR/webrtc/#rtcdatachannel)。

同时补短时拥堵、send失败、后台切换和WebGL丢失的明确结果。特别是房主的浏览器性能影响双方模拟推进；选择房主和网络质量都应进入诊断。恢复失败时至少释放输入并清楚结束，不让玩家只看到卡住。

**候选验收门槛：**直连、中继分别持续30分钟；覆盖受控延迟、抖动、丢包和5秒带宽收缩，报告分位数和退局率；人为跨路径乱序不导致重复动作或缺帧误判。现有150ms回调延迟检查不能替代网络丢包/重传测试。详见技术研究的测试矩阵。

完整rollback值得保留为研究原型，但当前不宜作为主线重写。先做单角色、无道具舞台的完整状态保存/恢复/校验与重跑预算；现有部分字段checkpoint和展示用观战快照都不等于完整存档。[GGPO作者文档](https://github.com/pond3r/ggpo/blob/master/doc/README.md)。

## 第四方向：用对局数据调整节奏和平衡

当前碰撞矩阵能证明招式在目标条件下命中，不能证明公平、好懂或有趣。14人的总生命为404–672，速度倍率为0.67–1.30；这些差异可以形成特色，也可能让某些打法难以应对。没有真人对局证据前不按生命值直接判强弱。

已有连击递减、脱身、连击保护、防御耐力与AI延迟观察。应重点测试这些机制之间的组合：

- 牛魔王高生命与全程霸体，是否能被侧移、跳跃、耗气、后摇惩罚有效克制；先前保护投技可破霸体的通用说法不适用于当前牛魔王。
- 6次受击保护后可爆冲追击，是否会连续接回长压制；记录防守者重新有可操作机会的时刻，而不只记录连击数字清零。
- 格挡疲劳与破防恢复，是否导致远程削血或简单重复重击成为通吃策略。
- 受击获得能量与高伤害必杀，是否频繁把节奏变成“挨打攒大招”；区分有趣的翻盘与难以理解的突然逆转。
- 布尔玛掩体/烟幕、饺子控制、乌龙变身是否有可见且有效的使用收益；娱乐角色可以有不同目标，不强求所有技能都以伤害评估。

复用现有 `combatDiagnostics`、战斗事件与 `runV2AIRounds` 做回归和策略漏洞扫描；AI对局胜率只能说明当前AI的使用方式，不能代替真人平衡结论。普通与困难AI已经分别采用0.24/0.12秒观察延迟，新增新手难度应降低持续压制与连招完成率、允许明显失误，不通过读取未来状态增强AI。

**第一轮样本建议：**4组朋友，先用悟空、克林、牛魔王、布尔玛覆盖全能/近战/霸体/远程，然后交换人物和房主，每组6局。共24局作为问题筛查，逐局保留角色、房主、网络、胜负、时长、脱身、破防、技能使用与再战意愿。它不足以估计稳定胜率；需要时再对可疑组合扩大样本。数值修改一次只针对一个机制，保留修改前后相同输入回归。

## 第五方向：内容制作围绕“为什么想再打一局”

第一项新内容建议是 **三场短连战的武道会路线**，复用现有角色、地图、CPU和胜利台词：选择角色后，依次遇到近战、远程、技术型对手，三场通关，结算展示这次表现并可立即重试。随机对手组合、可选挑战条件能产生变化；不需要新建大型剧情系统。

这条路线给“朋友还没上线”和“想熟悉另一个角色”提供目的。CPU难度和每场节奏由试玩调整；不要先照搬180秒×三局两胜到每站，导致小路线变成长流程。离线模式也能受益。

第二项内容是 **角色的关键反馈**：防反成功与失败、霸体承伤、控制递减、飞刃收回、变身解除分别有容易辨认的动作/声效/短提示。已有太阳拳、四臂、胜利演出应先统一清晰度，不让更多粒子淹没目标轮廓和可操作信息。

第三项内容是 **少量角色对手互动**：复用现有关系台词，在赛前和赛后形成一次短回应，可跳过且不增加漫长等待。首批围绕悟空/克林、龟仙人/悟空、雅木茶/布尔玛制作，用真实试玩判断是否加分，再扩大。

**候选验收门槛：**一条路线确实能完成、失败后能快速重试；玩家能辨认对手打法不同；至少有人主动换角色重玩。美术验收同时看实际对局、手机、分屏、观战，不只看图鉴摆拍。

## 第六方向：性能投入有实测条件

本机短测没有显示持续掉帧或GPU对象数量单调上涨。工程工作仍然有价值，但应优先解决第一次打开、手机激战和反复游玩的具体成本。

1. **背景图与缩略图。** 评估2.34MB PNG转换WebP/AVIF后的实际清晰度与下载量；将同一姿态、光照和镜头的14人/3地图缩略图从运行时移到构建时生成，保留自动再生成和对照检查。缩略图生成总建模/绘制成本须单独profiling，17次 `toDataURL` 的约52–56ms只代表导出调用，不能归因整个启动等待。
2. **已有合批之外的火花和碎屑。** 先在双方必杀、房屋倒塌、形态叠加时记录真实峰值，再试几何/材质池化或instancing。角色和场景已经做过合批，不能重复记为新增成果。实例化需同步观战导出，否则本地变快而观众漏画。
3. **减少无变化的HUD写入。** 当前每帧重复设置大量文字、宽度、aria属性；缓存已显示值，按变化更新。先查CPU profile，收益通常比“引入UI框架”更容易验证。
4. **菜单、暂停和恢复。** 当前循环仍在菜单/暂停绘制；根据实际可见动画决定降频或停止无变化绘制，同时保留音频和在线必要回调。不能为了省电冻结房主权威模拟。
5. **实体手机预算。** 至少一台中档Android与一台iPhone，连续15分钟，包含必杀、形态、建筑破坏、观战、切后台。记录帧间隔、温升/降频表现和系统内存；不能把M4上的触屏视口当手机性能。

先用同种子、同镜头、同输入做改前改后比较。画质档可让用户选择；常规画质不应因一次优化无提示降级。若降低draw calls没有降低GPU耗时，就检查透明过绘和像素成本，而不是继续合并一切。

## 建议交付顺序

| 阶段                    | 可交付内容                                                               | 放行依据                                                     |
| ----------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------ |
| A：让一组朋友完整玩起来 | 房间邀请、同房再战、偏好保留、可导出对局诊断；诊断中复现的传输缺陷先修   | 两台真实设备完成10场连续对局，双方输入和比分一致，无重复动作 |
